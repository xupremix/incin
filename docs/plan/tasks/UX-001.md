# UX-001 - automatic `Trainer` and the device-selection vocabulary

PROPOSALS.md §2's UX principles put this row at level 1 of three: "select three
devices and let Incin produce and explain a safe plan." Levels 2 and 3 - 
configured policy and explicit meshes - are the `DST-*` track. What makes level 1
a real level rather than a convenience wrapper is the sentence after it:

> "Easy" must not mean silent CPU transfer, hidden padding, relaxed determinism,
> or unbounded autotuning. Every automatic decision is inspectable and
> reproducible.

So the row is not "a loop that calls `backward` for you". A `Trainer` that
quietly runs on the CPU when the CUDA devices it was handed are absent is worse
than no `Trainer`, because the failure is a training run that finishes.

1. [x] Add the device-selection vocabulary Appendix A.8 assigns to this row:
   `DeviceSet` and `DevicePreference` in `incin-core::tensor::device`.
2. [x] Put availability behind a trait, the way `UX-014` put the doctor's
   hardware questions behind `Host`. A three-GPU machine has to be testable on
   a runner with none, or the row's own deliverable - "an unchanged model runs
   on CPU and on three GPUs" - is untestable here.
3. [x] Build `incin::train`: the builder from §2's example, a build report, and
   `fit`. The report is the deliverable as much as the loop is.
4. [x] Make an unsatisfiable device request an error carrying the report, never
   a fallback. This is the row's load-bearing property and the one most likely
   to be quietly "improved" into a fallback later, so it is pinned by tests
   that say so.
5. [x] Write `crates/incin/tests/trainer.rs`: the same model type trained on
   CPU for real, and planned against a mocked three-GPU machine.
6. [x] Run the row's evidence command plus `cargo fmt --check`,
   `cargo clippy --workspace --all-targets -- -D warnings`, and
   `cargo test --workspace`.

## Boundaries

`ParallelStrategy`, `StrategySet` and the plan objective belong to `DST-011`,
and `.explain()` as a rendered planning report belongs to `UX-005`, which
depends on both this row and `DST-011`. This row therefore builds the device
half of §2's example and not the `.parallel(ParallelStrategy::Auto)` half:
selecting devices, validating them, reporting what was selected, and training on
them. A builder method that accepts a strategy this workspace cannot yet plan
would be a field nothing reads.

Multi-device *execution* likewise waits for `DST-005`'s collectives. What this
row owes the three-GPU case is that the model type does not mention the device
set, that requesting three GPUs is validated rather than ignored, and that the
resulting report says what would run where - not that gradients are all-reduced.
The row is wrong if it claims otherwise, so `fit` on a multi-device set is an
explicit unsupported-operation error naming `DST-005`, not a silent single-GPU
run.

Appendix A.8 also lists `BackendKind` for this row. That type already exists
under the name `DeviceKind` - "the runtime-identifiable backend family a
`DeviceId` belongs to" - and adding a second spelling of it is exactly the
failure `D-008` records. `DeviceSet` is built from `DeviceKind`.

The row is `preview` tier, so per Appendix B it ships behind a non-default Cargo
feature.

## Outcome

Step 4 is the row. Everything else is a loop and a builder; the property worth
having is that `DeviceSet::cuda(0..3)` on a machine without three CUDA devices
is an error rather than a CPU run, and six of the sixteen tests assert a refusal
of one kind or another. The two failure modes are kept apart because their fixes
are: `NotCompiledIn` names the Cargo feature that would add the backend,
`DeviceUnavailable` names the device that is not there. A single "cannot use
CUDA" would have been true and useless.

`DevicePreference` and `DeviceSet` stayed two types for the same reason. A
preference is resolved against a machine and may end up somewhere the caller did
not name; a set is already resolved and may not. Collapsing them is what makes
"I asked for CUDA and got CPU" expressible, and §2 rules that out. `Fastest` is
the one variant permitted to reach the CPU, and even then every family it
skipped appears in the report - a fallback nobody can see is the silent one
under another name. The default is `Cpu` rather than `Fastest`, because a
default that moves an unchanged program onto a GPU the day one appears is the
same class of surprise as one that moves it off.

Step 5's CPU test initially asserted only that the final loss was finite, which
a `fit` that ran the forward pass and never stepped the optimizer would also
satisfy. It now probes the same model instance before and after training and
asserts the number changed. That change immediately failed, and the cause was
the fixture rather than the trainer: the model was `Linear -> ReLU`, and
`ReLU(Linear(ones))` can put every output unit on the flat side for an unlucky
initialization, making the gradient exactly zero. The fixture is a two-layer MLP
with the ReLU in the middle now, and the reason is written next to it.

The row's evidence command had to change. `cargo test -p incin --test trainer`
ran zero tests and reported `ok`, because Appendix B requires a preview-tier row
to ship behind a non-default feature and the suite is `#![cfg(feature =
"train")]`. Marking the row complete on that output would have been the exact
failure `UX-013` had just spent a row removing, so the command is
`cargo test -p incin --features train --test trainer`.

Six mutants, all caught and all compiling. Making an absent device fall back to
the CPU failed 3 tests, skipping the compiled-in check failed 1, running a
multi-device plan in `fit` failed 1, never stepping the optimizer failed 1,
dropping the skipped-family decisions failed 1, and clamping the epoch count to
one failed 1.
