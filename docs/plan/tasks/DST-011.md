# DST-011 — Two-rank hybrid planner and feasibility report

With two physical ranks there is no nontrivial rectangular product of DP, TP,
and PP degrees: the valid distributed layouts are DP=2, TP=2, or PP=2. The
hybrid planner therefore compares those three logical interpretations of one
shared, network-reachable two-rank physical topology.

1. [x] Define `ParallelOptions`, `ParallelStrategy`, `StrategySet`,
   `MemoryLimit`, and `PlanObjective`, reusing DST-010's
   `PipelineSchedule`.
2. [x] Define `TwoRankPlanningTopology`. A static mesh must prove
   `ValidMesh<World = U2>`; a runtime fingerprint checks two devices, a
   two-process world when applicable, both ordered links, and reachability.
3. [x] Define one checked `HybridWorkload` containing batch, tensor shard
   extent, parameters, per-microbatch activation, microbatch count, optimizer
   state copies, and both physical device capacities.
4. [x] Restrict static planning to floating `HybridPlanDType` implementations
   and reject the same integer/quantized dtypes through `Dyn`.
5. [x] Provide static DP, TP, PP, and automatic entry points. Static DP proves
   batch divisibility, TP proves tensor and parameter divisibility, PP proves
   parameter divisibility plus nonzero bounded microbatches, and static auto
   proves every candidate in its runtime-selected search set.
6. [x] Apply the matching runtime feasibility filters for `Dyn`, including
   exact two-way sharding and `ShardRemainderPolicy::Reject`.
7. [x] Model parameters, gradients, optimizer state, live activations, and
   schedule-dependent PP activation residency as checked per-rank peak bytes.
   Refuse any candidate that crosses its absolute or fractional device limit.
8. [x] Report exact shards, collective kinds/counts/bytes, per-rank memory,
   topology fingerprint, link class, transport, schedule, analytical step
   score, feasible candidates, Pareto frontier, and structured rejected
   alternatives.
9. [x] Order candidates by step-time, memory, or communication objective with
   deterministic tie breaking. The score is explicitly analytical rather
   than a measured duration.
10. [x] Prove equal static and `Dyn` reports, objective-dependent selection,
    schedule-dependent PP residency, memory filtering, runtime contract
    rejection, and five compile-time contract rejections.
11. [ ] Replace workload summaries with per-operation graph extraction once
    compiled distributed lowering is available.
12. [ ] Calibrate analytical weights through coordinated dry runs and
    measurements in DST-012/DST-013; do not treat the current score as a
    benchmark result.

## Local evidence

```text
cargo test -p incin-core --features distributed --test hybrid_plan
5 passed; 0 failed, including 5 compile-fail cases

cargo clippy -p incin-core --features distributed --test hybrid_plan \
  -- -D warnings
clean

cargo check -p incin-core --no-default-features --features distributed \
  --all-targets
clean
```

The compile-fail cases reject an integer static dtype, an odd DP batch, an odd
TP dimension, zero static PP microbatches, and a mesh whose type-level world is
not two. Runtime tests reject all integer/quantized dtypes, zero workload
fields, invalid memory fractions, an empty automatic search set, non-divisible
candidate dimensions, and over-budget candidates with structured reasons.

The initial estimates are deliberately conservative and reproducible. They
model communication payload rather than claiming a measured duration, and
they record the topology assumptions used to weight that payload. Because the
dependency strategies still await real two-host NCCL evidence and graph
extraction/calibration are later rows, DST-011 remains active rather than
complete.
