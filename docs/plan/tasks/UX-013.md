# UX-013 — feature and capability documentation generated from tested registrations

PROPOSALS.md sec. 2.10 states the deliverable as a prohibition rather than a
feature: "Do not maintain independent handwritten support tables that can drift
from code." The row is done when the support tables cannot drift, which is a
different thing from the support tables currently being right.

The second sentence is the other half: "Every public example is compiled in the
minimum documented feature set." That is what the row's evidence command
measures, and it currently measures almost nothing — `cargo test --workspace
--doc` reports 9 passed and 70 ignored, because 70 of the 79 public examples are
fenced `rust,ignore` and therefore compile nowhere.

1. [x] Establish the baseline both halves are measured against: what the
   handwritten tables claim, and how many public examples the evidence command
   actually compiles.
2. [x] Render the backend matrix from `CPU_CAPABILITIES`, `CUDA_CAPABILITIES`
   and `WGPU_CAPABILITIES` — the registrations `EXE-005` already tests — rather
   than from a hand-maintained copy of them.
3. [x] Render the feature tables from the Cargo manifests, which are the only
   authority on what a feature is named and what it enables.
4. [x] Make drift a build failure. A generator nobody runs is a handwritten
   table with extra steps, so the check has to run in CI and fail on a stale
   file, not merely offer to regenerate one.
5. [x] Compile the public examples. An example fenced `ignore` is not checked
   against the API it documents, so it documents whatever the API used to be.
6. [x] Run the row's evidence command plus `cargo fmt --check`,
   `cargo clippy --workspace --all-targets -- -D warnings`, and
   `cargo test --workspace`.

## Boundaries

Sec. 2.10 lists four things the capability manifest should generate. Two of them
already exist and are already driven off the registry: conformance test cases
(`EXE-010`) and `cargo incin doctor` operation probes (`UX-014`). This row
delivers the other two — the user-facing backend matrix and per-feature
reference documentation — and does not rewrite the two that are done. What it
does owe them is that all four read the same statics, so the row is wrong if it
introduces a second copy of the capability data to render from.

The row does not restructure the crate layout to let `incin-core`'s examples
name the facade's `DefaultBackend`. That is a dependency cycle whose cost lands
on the no_std feature-powerset check, and the visible text of an example is what
documents the API; which concrete backend satisfies its `B` parameter is not.

## Outcome

Step 1 is the reason the row is two halves rather than one. The handwritten
tables had already drifted — the facade matrix listed `candle`, which `GOV-006`
renamed to `external-candle` and left only as a deprecated alias, four lines
above an installation example using the new name — and it omitted `cpu-blas` and
`paranoid-validation` entirely. The examples were worse: 70 of 79 were fenced
`rust,ignore`, so `cargo test --workspace --doc` reported success having compiled
nine. Then `cargo test --all-targets` in CI turned out to exclude doctests, which
is why nothing had ever noticed. The row's own evidence command had never run in
CI at all.

The two halves have different authorities and so have different generators. What
a Cargo feature is called, whether it is on by default and what it enables are
facts about a manifest, so `cargo xtask docs` reads the manifests — including the
`#` comment above each feature, which is the only prose description of a feature
that already lives beside the thing it describes. What a backend supports is a
Rust static, so `incin_backends::capability_docs` reads
`CPU_CAPABILITIES`/`CUDA_CAPABILITIES`/`WGPU_CAPABILITIES` directly. Putting both
in `xtask` would have meant either parsing Rust or making `cargo xtask ledger`
compile the whole backend stack.

The summary table was a yes/no matrix first, and it was eleven rows of "yes":
all three backends register the same eleven operations. That reads as parity
when the backends are not at parity — CPU registers `reduction` for `f32` alone
and CUDA registers it for every float. The cell carries the element types now,
which is the question a reader actually has.

Step 5 is where the compiled examples paid. `from_slice` had been documented with
one argument and takes two — fifteen examples. `Param` was documented as
`Param<Tensor<S, B>>` and takes `<S, B>`. A rank-1 reshape's `Arg` is `((),)`,
not `()`. `dims()` returns an array for a static shape, not a `Vec`. The `s!`
macro's own example advertised `incin::symbolic_dim!`, which does not resolve:
`symbolic_dim!` is a `#[doc(hidden)]` alias for `dim!` in `incin-core` and the
facade does not re-export it. `incin-data`'s front-page example used a
`DataLoader::new(dataset).batch_size(32).shuffle(true)` builder against a
constructor that takes three arguments. Four backend placeholder names —
`DefaultBackend`, `MyBackend`, `Backend`, `IncinBackend<f32, Cpu>` — named one
concept; they are all `DefaultBackend` now, which is the one a user can write.

Three defects came out from under the examples rather than in them.
`IndexSpec` is the argument type of the public `Tensor::slice` and was not
reachable from the prelude, so the documented call could not be written; the
trybuild expectation that had to be regenerated is the proof, since rustc had
been rendering the full `incin::tensor::ops::index::IndexSpec` path for want of a
shorter one. `LSTM` and `LSTMCell` were absent from the prelude while `RNN` and
`RNNCell` one line above were present. And `DummyBackend`'s four binary ops
returned the left operand's shape unchanged, which is wrong for every real
backend: `broadcast_add` reaches `B::add` with differently shaped operands and
hands the result to `from_parts` against the broadcast type. That was invisible
because nothing had ever run a `broadcast_*` example.

Step 4 is what keeps the row done. Both generators have a check, both checks run
in CI, and a third test scans every `src` file for a reintroduced `ignore` fence
— a snippet that genuinely cannot compile where it lives is fenced `text`, which
says it is shown rather than checked and does not claim otherwise.
