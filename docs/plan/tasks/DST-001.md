# DST-001 - typed logical meshes and `ValidMesh`

PROPOSALS.md §3.8 opens the distributed track by splitting one question in two:

> **Logical proof:** model dimensions, shard counts, placements, collective
> semantics, and global/local output shapes.
> **Physical proof:** installed devices, rank mapping, available memory, peer
> access, link topology, transport versions, and communicator health.
>
> […] The API must call this *compile-time logical device selection and
> validation*, never compile-time hardware existence validation.

This row is the whole of the first half and none of the second. It answers "is
this a coherent parallel topology, and how many ranks does it describe?" without
consulting a machine. `DeviceMesh::bind`, the topology fingerprint, and the
runtime guards are `DST-002`.

1. [x] Add a non-default `distributed` feature to `crates/incin-core`, the name
   already used by the ledger for `incin-macros` and by `incin-backends` as
   `distributed-reference`. Appendix B requires a preview-tier row to ship
   behind one.
2. [x] Write `crates/incin-core/src/dist/mesh.rs`: the `Data`, `TensorParallel`,
   and `Pipeline` axis markers and `MeshSpec<DP, TP, PP>` from §3.8, with the
   omitted axes defaulting to one the way `mesh![dp = 3]` will.
3. [x] Implement `ValidMesh` over the typenum `Mul` engine the shape rules

4. [x] Write `crates/incin-core/tests/mesh_compile.rs`: the three valid

## Boundaries

`DeviceMesh`, `MeshId`, `CollectiveGroups`, and `TopologyFingerprint` are
Appendix A's `DST-002` row and are not built here. Nothing in this row holds a
`DeviceId`, and that is the point: §3.8 warns that a static device marker
encodes a *requested* family and ordinal, never an installed one, so a type that
mixed the logical degrees with the physical devices would be claiming the
compile-time hardware validation §3.8 rules out.

Shard divisibility - "three-way tensor parallelism additionally requires
relevant hidden, vocabulary, or attention-head dimensions to divide by three" - 
is `DST-003`'s `Div`/`Rem` work on placements, not this row's. This row proves
the mesh, not what is placed on it.

`mesh![dp = 1, tp = 3, pp = 1]` is `UX-002`, which depends on this row. The
types have to be writable by hand first, and writable by hand is also the case
the macro will not cover.

The mesh types stay out of `incin_core::prelude`. `Data` and `Pipeline` are
common enough words that a glob prelude re-exporting them changes what
`use incin::prelude::*` means for existing code the day a preview feature is
enabled, which is the reverse of what a non-default feature is for.

The `incin` facade gains no `distributed` feature either. Nothing there accepts
a mesh yet - `DeviceMesh` is `DST-002` and placements are `DST-003` - so
forwarding it would expose a type with no verbs, and it would double the
facade's feature-powerset job in CI to do it. `DST-002` is where the facade
gains something to enable.

## Outcome

`ValidMesh` has exactly one implementation, and that is the whole design. Every
way of being an invalid topology - a zero degree, an axis marker in the wrong
position, a world size the caller did not ask for - is the absence of that
implementation rather than a check something has to remember to call. §3.8's
two requirements, "nonzero axes and checked `DP × TP × PP` multiplication on
stable Rust", are both bounds: `NonZero` is `typenum`'s own marker and is not
implemented for `UTerm`, and the product is the same `Mul` the shape rules use,
so a mesh and a shape agree about multiplication by construction rather than by
review.

`World` is an associated type rather than only a constant because a `usize`
cannot be bounded on. `M: ValidMesh<World = U3>` is what turns §3.8's sentence
about three GPUs into a compile error for the `2 × 2`; `WORLD` stays a defaulted
projection of it so no implementation can set the two independently.

The axis-order case is the one worth the third compile-fail file. `Data<U1> ×
Pipeline<U3> × TensorParallel<U1>` is three ranks either way, and the swap turns
three-way tensor parallelism into three pipeline stages with nothing downstream
noticing. A single `MeshAxis` bound on all three parameters would have accepted
it.

Two things the row inherited rather than invented. The evidence command carries
`--features distributed` for the reason `D-053` records: a `cfg`-gated suite run
without its feature reports `ok` having run nothing. And CI now runs the
preview-tier evidence commands for this row and `UX-001`, because the powerset
job runs `cargo hack check` - which compiles a trybuild suite without executing
it - and the default test job enables neither feature. `UX-001`'s suite had been
running nowhere at all.

Five mutants, all caught. Allowing a zero axis failed the trybuild case,
reporting the pipeline degree as the tensor degree failed 2 tests, a second impl
for the swapped axis order failed the trybuild case, and defaulting the omitted
axes to the wrong markers failed the suite to compile. The fifth - dropping the
pipeline axis from the product - does not compile the library at all: `World` is
bounded `Unsigned` and `Prod<DP, TP>` is not known to be one, so the bound
rejects that mutation before any test runs.
