# GRD-005 — structured backward and NaN failures

PROPOSALS.md sec. 3.9 states both halves in two sentences: "Backward closures
must return structured errors. NaN checking is an execution policy applied
consistently across backends, not a panic-only backend helper."

Neither holds today. `BackwardFn<S>` is `Fn(&S) -> Vec<S>`, so a recipe that
cannot produce a gradient has exactly one way to say so, and 115 sites across
the three backends take it — `.expect("unbroadcast lhs (add)")`,
`.unwrap()` on a fallible elementwise kernel, and so on. And NaN checking is a
second entry point, `Backend::backward_with_nan_check`, which panics: a caller
choosing it changes both *what is checked* and *what happens on failure*, and a
caller who wants the check without the abort has no spelling at all.

1. [x] Add `BackwardError` to `crates/incin-core/src/err.rs`, on the model of
   the `BackendError` that is already there, and a transparent `Error` variant
   carrying it. A non-finite gradient names the tensor it was found on; a
   failed recipe names the operation.
2. [x] Make `BackwardFn<S>` return `Result<Vec<S>>` and have the walk propagate
   rather than the recipe abort. `EXE-008` recorded this as pending and
   attributed it to `GRD-001`, which has since landed without it; this is the
   row that owns error typing.
3. [x] Turn `NanCheck` — the walk argument `GRD-003` introduced — into a
   `NanPolicy` axis on `ExecutionPolicy`, beside `MathMode`, `Determinism`,
   `FallbackPolicy`, `AllocatorPolicy`, and `GradMode`. That is what "an
   execution policy applied consistently across backends" means concretely: one
   ambient value, read by the one walk all backends share.
4. [x] Delete `Backend::backward_with_nan_check` and its four implementations.
   With the check on the policy, a second method is a second way to ask the
   same question, and `D-008` rules against ending up with both vocabularies.
5. [x] Convert all 115 panic sites inside backward recipes to `?`.
6. [x] Write `crates/incin-core/tests/backward_errors.rs`: a non-finite
   gradient is a returned error naming its tensor, the default policy does not
   pay for the check, a recipe failure propagates rather than aborts, and the
   gradients a successful pass produces are unchanged by any of it.
7. [x] Run the row's evidence command plus `cargo fmt --check`,
   `cargo clippy --workspace -- -D warnings`, and `cargo test --workspace`.

## Boundaries

WGPU and CUDA recipes are edited here only to satisfy the new signature. Their
*behaviour* on hardware is `GRD-004`, which this host cannot run.

Roughly twenty of the converted sites carry an `expect` message asserting the
call cannot fail — "shapes proven compatible", "same element count". Those
messages do not survive as comments. The claim they make is exactly the one a
fallible signature makes unnecessary: an error that cannot occur costs a `?`
and never fires, whereas asserting impossibility with a panic is the thing this
row exists to remove.

## Outcome

Step 5 found five sites that were not the mechanical change the rest were: an
`unwrap` on an `Option` cannot become a bare `?`, so the compiler surfaced four
convolution group lookups and one embedding axis index that needed an error of
their own rather than a propagation.

Step 3 turned out to reach further than the plan said. CUDA had no NaN check at
all — `backward_with_nan_check` delegated to `backward` — so "applied
consistently across backends" meant giving it one, and doing that surfaced its
accumulation unwrapping a kernel launch inside `and_modify`.

Step 6's first draft asserted `tensor > 0 || tensor == 0`, which is true of
every `u64`. The mutant that reports a fixed id passed it. It names the exact
operand now.
