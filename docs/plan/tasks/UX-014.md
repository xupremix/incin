# UX-014 - `cargo incin doctor`

PROPOSALS.md sec. 2.3 specifies the command and is explicit that it is an
extension rather than a new binary: `cargo-incin` already has a subcommand
dispatcher, and `doctor` joins it. The section lists what the report must
cover, and closes with the two properties that make it a support tool rather
than a print statement - "The command is read-only unless invoked with an
explicit cache-cleaning or benchmark flag. Its output has stable
human-readable text and optional JSON for CI/support reports."

The row's own evidence command is `cargo test -p incin --test doctor`, an
integration test. An integration test links the *library*, not the `[[bin]]`,
so a doctor written inside `cargo-incin.rs` cannot be reached by the command
that is supposed to prove it works. The report therefore lives in
`crates/incin/src/doctor.rs` and the binary is the dispatcher the section
describes.

"Mocked hardware tests" is the other half of the same constraint. A report
assembled from ambient hardware asserts nothing on a machine without a GPU,
which is every CI runner here. Every impure observation goes behind one `Host`
trait; assembling the report, deriving its findings, and rendering it are pure
functions of that trait's answers.

1. [x] Define `Host` - the whole impure surface: toolchain version, which
   backend families this build compiled in, which of them answer right now,
   the CPU ISA the kernels branch on, the caches, the enabled features.
   `HostMachine` is the real implementation; a test supplies its own.
2. [x] Assemble `Report` from a `Host`, covering sec. 2.3's list restricted to
   what exists today. Metal is `MTL-001` and unbuilt; a row claiming to have
   checked it would be a false negative.
3. [x] Derive findings as a pure function of the report. Each carries a stable
   code, because a support workflow greps for the code and reads the prose.
   The one sec. 2.3 names explicitly - "warnings when a feature is compiled but
   its runtime is unavailable" - is `backend-unavailable`.
4. [x] Render stable text and JSON. Stable means pinned by a golden test, fixed
   section order, and a `schema_version` in the JSON so a consumer can tell
   when it changed.
5. [x] Wire `doctor` into the dispatcher and the help text, with `--json`.
6. [x] Write `crates/incin/tests/doctor.rs`: every finding provoked by a mocked
   host, the golden text, the JSON shape, read-only-ness, and one smoke test
   against the real machine.
7. [x] Run the row's evidence command plus `cargo fmt --check`,
   `cargo clippy --workspace -- -D warnings`, and `cargo test --workspace`.

## Boundaries

No cache cleaning and no benchmark flag. Sec. 2.3 permits them as explicit
opt-ins; neither is required by the row's deliverable, and a destructive flag
whose only test would be that it deletes things is not something to add
speculatively. What the row does owe is the default: the doctor must not write
anything, and that is asserted rather than asserted-about.

`plan` and `tune` are named beside `doctor` in the same sec. 2.3 sentence.
They belong to `TUN-005` and the planning rows, not here.

## Outcome

Step 3's first draft made a rejected probe a finding, and the healthy-machine
test showed what that costs: an ordinary CPU laptop opened its report with two
notes saying `f16` matmul and `f64` reduction are unsupported, which is not a
fault, is not actionable, and is already printed in the probe section a few
lines above. It is reported and not concluded now, and a test pins the decision
because the obvious "improvement" is to add it back.

Step 6 found a real defect, and it was not in the doctor. `cargo test
--workspace` unifies the `wgpu` feature into `incin`, and under it the suite
died with a `SIGSEGV` rather than a failure. The doctor's own share of it was a
bug - `gather` probed each family twice, once to report it and once to decide
whether to probe its capabilities - but fixing that only reduced how often the
crash reproduced. Underneath, `detect::probe_wgpu` built a `wgpu::Instance` per
call and dropped it, and two threads each probing twice took the process down
three times out of three. `cargo incin doctor` was simply the first caller ever
to probe the same family more than once in one process. The instance is shared
through a `OnceLock` now, matching what `wgpu::device::get_device_state`
already does, and `detect.rs` carries the regression test - which segfaults
without the fix.

Step 7 found the third. Pinning the subcommand's exit code to zero failed the
`--no-default-features --features std` build, where no backend is compiled and
`no-backend-compiled` correctly fires. That was the diagnostic working, so the
test compares against the report's own verdict, and a second test asserts the
real build agrees with the mock about whether it can run anything. The error
path is exercised by the feature powerset now rather than only by a mock.
