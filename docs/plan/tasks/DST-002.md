# DST-002 - physical binding, the topology fingerprint, and the runtime guards

`DST-001` built the half of PROPOSALS.md §2.11 that a compiler can check. This
row builds the other half, the one §2.11 says is not checkable at all until a
process looks at a machine:

> **Physical proof:** installed devices, rank mapping, available memory, peer
> access, link topology, transport versions, and communicator health.
>
> […] Binding validates device count and uniqueness, backend/dtype
> capabilities, required collective groups, peer access, hard topology
> requirements, estimated peak memory, and agreement on rank/process/
> communicator identity. A topology fingerprint includes stable device
> identity, architecture, relevant link classes, transport/library versions,
> and process layout. Device ordinal alone is not a valid persistent identity.

Both halves land in `crates/incin-core/src/dist/mesh.rs`, which is the target
column of both rows. They are adjacent on purpose: the failure §2.11 is warning
about is a type that makes the logical claim and the physical one at once, and
the boundary is easier to hold when both sides of it are on the screen. No type
above `DeviceMesh` in that file gains a device.

1. [x] Add the observation seam. `TopologyProbe` is every question binding asks
   the machine - a device's stable identity, the link class between two
   devices, the transport version, the process layout - and nothing else in the
   module reads hardware. This is `UX-014`'s `Host` applied to the same problem:
   the row's evidence has to run on a CI machine with no GPUs.
2. [x] Add the fingerprint vocabulary: `DeviceIdentity` (the ordinal the caller
   asked for *plus* the device's own persistent id and architecture, because
   §2.11 says the ordinal alone is not one), `LinkClass`, `TransportVersion`,
   `ProcessLayout`, and `TopologyFingerprint` over them.
3. [x] Give the fingerprint a stable digest and derive `MeshId` from it and the
   logical degrees, so two processes that bound the same machine the same way
   compute the same id without talking to each other.
4. [x] Add `CollectiveGroups`: the rank layout convention and the data, tensor,
   and pipeline groups it induces. Groups are computed from the degrees on
   demand rather than stored, so there is no second copy to disagree.
5. [x] Add `DeviceMesh<M>` and `DeviceMesh::<M>::bind`, with one `BindError`
   variant per guard: count against `M::WORLD`, repeated ordinals, one physical
   device reached through two ordinals, a device the probe cannot see, a mixed
   backend family, a mixed architecture, an unsupported process layout, and a
   tensor-parallel group whose members cannot reach each other.
6. [x] Write `crates/incin-core/tests/mesh_bind.rs` against a fake machine: the
   three-GPU bind §2.11 shows, every rejection, the rank/coordinate round trip,
   and `MeshId` stability.
7. [x] Run the row's evidence command plus `cargo fmt --check`,
   `cargo clippy --workspace --all-targets -- -D warnings`, and
   `cargo test --workspace`; add the row's command to CI's preview-feature step.

## Boundaries

**No real probe ships in this row.** `TopologyProbe`'s implementors are
`DST-005` (the deterministic CPU reference transport) and `DST-006` (NCCL). A
probe that answers questions about CUDA link topology has to call CUDA, and
`incin-core` is `no_std` and talks to no device - that is the crate layering,
not a shortcut. What core owns is the seam and every decision made from its
answers, which is the part with rules in it.

**Capability and memory validation are not here.** §2.11's binding list
includes "backend/dtype capabilities" and "estimated peak memory". The first
needs a `CapabilityRegistry` per rank, which arrives with the backends in
`DST-005`/`DST-006`; the second needs a plan to estimate, which is `DST-007`.
`EXE-005` is a dependency of this row because binding will consult the registry
through the same `Capabilities` trait, not because this row consults it.

**Communicator health is not here.** §2.11 lists it under physical proof, and
it is the one item that cannot be answered by inspection - a communicator has
to exist first. `DST-006` creates communicators.

**Placements are `DST-003`.** `DeviceMesh` is what a placement will name; it
does not name one. Nothing in this row constructs a `PlacementKind`, and
`MeshId` exists as the handle those variants will carry.

**`mesh![...]` is `UX-002`** and the `incin` facade still gains no
`distributed` feature. `DST-001` deferred that to "where the facade gains
something to enable"; a `DeviceMesh` that no tensor can be placed on is still
not that, because placement is `DST-003`. The facade gains the feature when
something in it takes a mesh.

## Outcome

Landed 2026-07-29. `cargo test -p incin-core --features distributed --test
mesh_bind` → **17 passed, 0 failed**; eleven mutants, all caught.

Three things came out different from the plan above, and all three are recorded
in Appendix C.

**Step 5's reachability guard covers every axis, not just tensor.** The plan
named "a tensor-parallel group whose members cannot reach each other". Written
that way the guard would accept a data-parallel pair with no path between them,
which cannot run the all-reduce that axis exists for. `BindError::UnreachableGroup`
names the axis instead, and only `LinkClass::Unreachable` is refused - a slow
link is a performance judgement, not a correctness one (D-062).

**Step 4's groups are computed over an axis array rather than three named
degrees.** Same behaviour, one property: adding §2.11's expert-parallel axis
later is an array entry rather than a re-derived rank convention (D-061).

**`DeviceMesh`'s `Debug`/`Clone`/`PartialEq`/`Eq` are written out, not derived.**
`derive` bounds them on `M: Debug + …`, and `M` is a `MeshSpec` - a marker that
is never constructed and implements none of them - so the derived bounds make a
`DeviceMesh` undebuggable for exactly the type parameters it exists for. Caught
by the test suite failing to compile, not by review.

Two things the evidence itself changed. A first mutation run showed nothing
covered the digest's per-field length prefix, so
`adjacent_fingerprint_fields_cannot_be_confused_for_each_other` was added and
the mutant then failed it. And one mutation was rejected as unfaithful rather
than recorded as a survivor: zeroing `M::DATA` alone leaves `MeshId` unchanged
in every reachable case, because two meshes differing only in their data degree
have different world sizes and so cannot bind the same devices. Removing all
three degree terms - the mutation the plan actually meant - fails
`one_machine_bound_two_ways_has_two_ids`.

One cost this row imposed on `DST-001`, recorded rather than absorbed.
`MeshAxis`'s variants are `Data`, `Pipeline`, and `Tensor`, which shadow the
marker type names, so rustc now fully qualifies `incin_core::dist::mesh::Data`
in `mesh_axes_out_of_order.stderr` and `mesh_zero_axis.stderr` - DST-001's
headline diagnostic is longer than it was. The baselines were re-blessed with
`TRYBUILD=overwrite`. Nothing about what those cases assert changed: both still
fail with `E0277` and both still pass `every_mesh_case_names_the_rule_it_pins`,
which is the guard that pins them by reason rather than by rendering (D-064).

Everything under **Boundaries** above held: no probe implementor ships, no
capability or memory validation, no communicator, no placement, no `mesh!`, and
the `incin` facade still gains no `distributed` feature.
