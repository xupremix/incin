# GRD-003 — backend-neutral tape nodes

PROPOSALS.md sec. 1.2.5: "The core owns a backend-neutral graph containing
operation kind, dependencies, saved-value handles, and backward recipe. Each
backend supplies kernels for the backward recipe."

Today there are three graphs and the core owns none of them. `cpu/tape.rs`,
`wgpu/tape.rs`, and `cuda/tape.rs` each declare their own `TensorId`, their own
`TapeEntry`, their own thread-local `Vec`, and their own copy of the same
reverse walk — drain first, walk in reverse, accumulate rather than overwrite.
The walks are not similar by coincidence; they are the same algorithm written
three times, and the CPU one carries a comment marking the exact line where
writing it a second time reintroduced an overwrite bug (`CPUBACK-05`).

1. [x] Write `crates/incin-core/src/exec/tape.rs`: one `TensorId`, a
   `TapeStorage` trait naming exactly what a reverse walk needs of a backend's
   storage, a `TapeNode<S>` holding the dependencies and the backward recipe,
   a `Tape<S>` owning the nodes, and `GradientMap<S>` holding the result.
2. [x] Put the walk there, once. Drain before invoking anything (D-06),
   accumulate through an entry API that cannot be spelled as an overwrite
   (`CPUBACK-05`), and skip an output nothing reached rather than failing.
3. [x] Make accumulation fallible, because one of the three backends already
   is: WGPU's `add_wgpu_storage` returns a `Result` and CPU's addition cannot
   fail. A shared walk has to carry the weaker guarantee.
4. [x] Reduce `cpu/tape.rs` to a `TapeStorage` impl, the thread-local that owns
   the tape, and the CPU-specific `unbroadcast` helper. The three backend-local
   thread-locals stay put — `GRD-006` owns deleting them, and this row owns the
   node type and the walk they hold.
5. [x] Unify `TensorId`. Three identical `TensorId(u64)` newtypes over three
   independent counters become one, re-exported from each backend so no call
   site changes.
6. [x] Prove CPU parity. The row's evidence command names `current backend gradient tests`
   under `--features std,cpu`, and that file is `#![cfg(all(feature = "cpu",
   any(feature = "wgpu", feature = "cuda")))]` — it compiles zero tests under
   the command that is supposed to prove it. Add the CPU-side cases so the
   command tests something.
7. [x] Run the row's evidence command plus `cargo fmt --check`,
   `cargo clippy --workspace -- -D warnings`, and `cargo test --workspace`.

## Boundaries

WGPU and CUDA keep their own walks in this row. Moving them is `GRD-004`
("CUDA and WGPU gradient recipes with hardware parity"), and their parity is
asserted on hardware this host does not have; migrating them here would mean
changing two backends whose evidence cannot be produced.

The backward closure signature stays `Fn(&S) -> Vec<S>`. `EXE-008` recorded
that making it fallible touches nineteen WGPU closures and deferred it to "the
explicit gradient context"; the row that owns error typing is `GRD-005`
("structured backward and NaN failures; no expected-failure panic paths"), and
the `panic!` in the NaN check moves as-is rather than being redesigned here.

`TapeNode` does not carry the operation kind sec. 1.2.5 lists. Supplying it
means editing 116 push sites to name a value nothing reads, and this repository
has already ruled twice — `GRD-001` on `GradMode`, `TUN-003` on
`AutotunePolicy` — that a field a caller can set and nothing consumes is a
worse contract than a missing one. It belongs to the first row that reads it.

## Outcome

Step 2 changed shape under test. The walk was written as `Tape::backward(&mut
self, ..)` and four convolution tests failed immediately with `RefCell already
borrowed` — conv backward records while it runs. It takes `Vec<TapeNode<S>>` by
value now, which is `D-024`, and makes `D-06` structural instead of advisory.

Step 6 found that the row's evidence command tested nothing at all, and the
first mutant run found that a forward-order walk passed every CPU case, because
each was one operation deep. The three-factor chain test exists for that.
