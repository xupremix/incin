# EXE-010 — external-backend SDK conformance suite and template

PROPOSALS.md sec. 2.9 lists seven things the backend-authoring surface has to
contain, and closes with the property that makes it an SDK rather than a set of
traits: "An external backend implements only the operation descriptors it
supports. Missing support is visible through the capability registry rather
than hundreds of default trait methods."

That sentence is what the conformance suite has to enforce, and it is the
reason the suite cannot be more tests in `candle_executor.rs`. A conformance
suite is only worth the name if a backend author can point it at their own type
and get a verdict, and if an operation they did not implement *skips* rather
than fails. Both of those make it generic over the backend, not over Candle.

1. [x] Make `--features external-candle` lint-clean. The row's evidence command
   builds that feature set, and `cargo clippy -- -D warnings` currently fails
   on it: `bytes` is gated on `external-candle` among others, but the Candle
   adapter never allocates by byte length, so `byte_len` is dead there.
2. [x] Build `external::conformance` — the harness sec. 2.9 calls "conformance
   tests" and "numerical tolerance profiles". A `Subject` trait carries the
   three things only the author can supply: their backend, storage built from
   values, and values read back. Everything else is the harness's.
3. [x] Drive every check off the capability registry, so a backend that
   registers `MatMul` and not `Conv2d` is checked on the first and skipped on
   the second. A suite that fails a backend for an operation it never claimed
   is a suite nobody runs.
4. [x] Check what an author actually gets wrong: metadata that disagrees with
   the tensor it describes, an executor that runs an operation its registry
   calls unsupported, an output shape that disagrees with the validated
   descriptor, a wrong input arity that panics instead of erroring, and
   numerics outside the declared tolerance.
5. [x] Write the template — a complete minimal backend, in the repository, that
   an author copies. Prose describing the seven bullets would go stale; a
   backend that compiles and passes the suite cannot.
6. [x] `crates/incin-backends/tests/conformance.rs` runs the suite over both
   the template and Candle. The template is the control: a harness that has
   never passed a known-good backend proves nothing about the one it fails.
7. [x] Run the row's evidence command plus `cargo fmt --check`,
   `cargo clippy --workspace -- -D warnings`, and `cargo test --workspace`.

## Boundaries

Sec. 2.9 also lists "autograd parity tests" and "rules for synchronization,
ownership, and device errors". The Candle adapter implements `Execute` for two
descriptors and records no tape, so an autograd conformance check would have
nothing to run against and no second implementation to be parity *with* —
`GRD-004` is where a second backend's recipes appear. Ownership and device
errors are checked where they are observable today: storage validated at the
boundary, and a foreign handle rejected rather than panicked on.

The suite does not grow the Candle adapter's operation coverage. Two
descriptors is what `EXE-008` migrated and what this row measures; adding a
third would make the row about Candle rather than about the surface.

## Outcome

Step 1 was larger than "make the lints pass". `bytes` was gated on
`external-candle` among the GPU backends, but the Candle adapter never
allocates by byte length — Candle owns its own allocations — so
`--features external-candle` without a GPU compiled a module whose only
function was dead. The `unsupported` macros one line below keep that gate,
because Candle does use those. The other failure was a one-character
`needless_borrow`.

Step 2 moved a module boundary. `pub mod external` was gated on
`external-candle`, which put the backend-authoring surface behind one
particular integration: an author writing a backend for an ecosystem this
repository has never heard of would have had to enable the Candle adapter to
test it. The module is unconditional now and `candle` inside it keeps the gate.
`cargo test -p incin-backends --no-default-features --features std,external-candle
--test conformance` passes with no native backend compiled at all, which is
what makes that a real seam rather than a rearrangement.

Step 5 found the limit of `Dyn`. The matmul fixture lowers dynamically, and the
reshape fixture cannot: `ReshapeShape` carries an `ElementCount` proof that
`Dyn` has no way to supply, so a dynamically shaped reshape has nothing to
lower. That is the rule working — element count is exactly what reshape has to
preserve — and it means the harness fixes its reshape shape pair rather than
taking it as an argument.

Step 6 is where most of the value is, and it is the half a conformance suite
usually skips. A suite that has never failed a backend is indistinguishable
from one that cannot, so four deliberately broken backends sit beside the
template: one whose registry claims everything, one that indexes its inputs
instead of matching on them and therefore panics on a wrong arity, one that
multiplies its operands the wrong way round with a correct output shape, and
one that registers nothing at all. Each is asserted to fail exactly the check
it breaks — no more, so the checks are independent, and no fewer, so none is
vacuous. The last one must *pass*, with five checks skipped: sec. 2.9 says a
backend implements only what it supports, and a suite that fails a half-written
backend is one authors route around.
