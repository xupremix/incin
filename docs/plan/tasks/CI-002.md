# CI-002 — scheduled CUDA and WGPU hardware matrix

1. [x] Establish what the repository can actually run: `xupremix/incin` has zero
   registered self-hosted runners, and no GitHub-hosted runner offers an NVIDIA
   device, so a CUDA job that names a hardware label queues until it times out
   rather than reporting anything.
2. [x] Add `.github/workflows/hardware.yml` with a weekly schedule and a
   `workflow_dispatch` `job` input, matching the invocation the later CI rows
   already record as their evidence.
3. [x] Resolve which jobs run in one `select` job, so an unavailable runner is
   reported as a stated reason rather than a queued job, and so a job name owned
   by an unimplemented row names the row that owns it.
4. [x] Run the WGPU matrix over both a software adapter, which every scheduled
   run can reach, and an optional native adapter behind a runner variable.
5. [x] Run the CUDA suites the EXE-004, EXE-005, and EXE-008 hardware
   obligations name, including the `--ignored` sets, behind the same runner
   variable.
6. [x] Assert each hardware job actually executed tests, because a filtered or
   device-less run reports success with zero tests and is indistinguishable from
   a pass by exit code alone.
7. [x] Record device and driver metadata in the job summary so a failure can be
   attributed to a device, a driver, or the code.
8. [x] Validate the workflow, run the full local gate, and record evidence plus
   the deviation covering what could not be proved without a registered runner.

The scheduled CUDA job cannot execute until a GPU runner is registered and
`HARDWARE_CUDA_RUNNER` is set. That is a repository administration step, not a
code change, and the workflow states the omission rather than passing silently.
`CI-003`, `CI-004`, and `CI-007` extend the `job` input with `dist3`,
`multinode`, and `metal`; this row deliberately implements none of them.
