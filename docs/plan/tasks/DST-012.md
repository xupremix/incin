# DST-012 — Coordinated two-rank collective tuning

Collective tuning is a distributed protocol, not two independent local
benchmarks. Every rank must measure the same legal candidate against dedicated
state, and the slowest rank determines completion. A winner cannot enter a
cache until all ranks agree on the exact problem, candidate, and score.

1. [x] Define a stable `CollectiveTuningKey` containing collective and
   reduction semantics, dtype, message-size bucket, exact group, topology
   fingerprint, transport/version, and determinism policy.
2. [x] Define static collective-operation markers for all-gather, all-to-all,
   all-reduce, reduce-scatter, and both PP=2 send directions. Static reduction
   dtype and two-way divisibility errors fail compilation.
3. [x] Define the matching `new_dyn` path with runtime dtype, reduction,
   cardinality, group-size, peer, topology, workspace, and message-byte
   validation.
4. [x] Define static and runtime algorithm/protocol/channel/chunk candidate
   descriptors with stable cross-rank hashes and bounded channel, chunk,
   priority, workspace, and determinism filters.
5. [x] Define static and runtime nonzero tuning budgets that bound both
   candidate count and synchronized samples per candidate.
6. [x] Require one successful, identity-matching report from each rank for
   every candidate, and reject missing/duplicate ranks, wrong hashes, sample
   count drift, launch failure, and mutation of dedicated measurement buffers.
7. [x] Score each synchronized sample by the maximum rank duration, then take
   the median of those maxima. Retain per-rank medians for imbalance
   diagnostics and use stable candidate hash as the tie breaker.
8. [x] Separate `ProvisionalCollectiveTuning` from
   `CommittedCollectiveTuning`; only two unanimous votes for the exact problem,
   candidate, and maximum-rank score mint the committed type.
9. [x] Prove static/`Dyn` identity parity, topology invalidation,
   maximum-rank-versus-average selection, buffer integrity, bounded search,
   and partial/mismatched/rejected commit failures in pure tests compiled under
   both reference and NCCL features.
10. [x] Add four compile-fail cases for block-quantized collectives, integer
    mean reduction, odd all-to-all cardinality, and zero static channel count.
11. [x] Integrate these contracts with TUN-003's general tuning policy,
    distributed permit, and cache service after that dependency lands.
12. [ ] Expose verified NCCL algorithm/protocol/channel controls and measure
    real synchronized CUDA events on dedicated buffers and streams. The
    current candidate descriptors do not claim that cudarc/NCCL applied them.
13. [ ] Run candidate broadcast, barriers, measurement, failure injection, and
    unanimous commit on two network-accessible CUDA/NCCL hosts.

```text
  --all-targets -- -D warnings

```

The selection fixture deliberately gives candidate A rank durations of 1ns and
100ns and candidate B durations of 60ns and 60ns. A cross-rank average would
choose A (50.5ns), but collective completion is gated by its 100ns slow rank,
so the required maximum-rank objective chooses B at 60ns.

This row remains active. Its coordination state machine and TUN-003 service
commit are locally testable and transport-neutral, but the current NCCL wrapper
does not expose verified per-launch algorithm controls, and this workspace has
only one CUDA device and no second network endpoint. Those missing pieces are
hardware/service evidence, not conditions the pure coordinator should pretend
to satisfy.
