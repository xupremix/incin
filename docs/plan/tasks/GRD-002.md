# GRD-002 — `G` to `GradMode` propagation

PROPOSALS.md sec. 1.2.5 states the contract in one sentence: "`NoGrad` must
produce no autograd node and save no backward-only tensor." Today the backends
cannot honour it, and `cpu/tape.rs` says so at the declaration of `push` — per
D-05 it records every operation unconditionally, "the backend has no visibility
into whether the surrounding `Tensor<..., G>`'s `G` is `Grad` or `NoGrad`."
The typed marker is known at the frontend and the recording happens three
crates down, with nothing carrying the decision between them. This row is that
carrier.

1. [x] Add `GradMode` to `exec::policy` and a `grad_mode` field to
   `ExecutionPolicy`, the field GRD-001 deliberately left out because nothing
   read it yet. Give it `current()` and `scope()` over the thread-local
   `ExecutionPolicy` GRD-001 already installs, so a grad decision is the same
   kind of ambient value as every other policy axis rather than a second
   mechanism beside it.
2. [x] Derive `GradMode` from the existing markers in `tensor/grad.rs`:
   `RequiresGrad::grad_mode` for the runtime-resolved case and
   `ConstRequiresGrad::GRAD_MODE` for the compile-time-fixed one. Both derive
   from `requires_grad`/`REQUIRES_GRAD` rather than being supplied per impl, so
   a marker cannot claim one thing about gradients and another about recording.
3. [x] Give `ExecutionContext` the matching `grad_mode()` accessor and
   `with_grad_mode()` builder, so the explicit form spells the decision exactly
   as sec. 2.1 writes it.
4. [x] Propagate. Every core operation that reaches a backend method which
   records runs that call under the mode its result's `G` derives:
   `tensor/ops/{binary,unary,reduce,manipulation,loss,module}.rs`,
   `tensor/matmul.rs`, `tensor/conv2d.rs`. `Grad` installs nothing — an
   enclosing `no_grad` scope must win over an operand that merely permits
   recording — so the propagation costs a `NoGrad` operation one thread-local
   write and a `Grad` one nothing at all.
5. [x] Gate the three backend tapes. `cpu`, `wgpu`, and `cuda` `push` return
   without recording when the ambient mode does not record. One gate per tape
   rather than one per call site: there are 116 push sites and a guarantee that
   depends on 116 correct edits is not a guarantee.
6. [x] Make the guarantee observable. `tape::len` is `#[cfg(test)]` and so
   cannot be seen from an integration test; a promise that nothing outside the
   crate can check is not evidence.
7. [x] Write `crates/incin-core/tests/nograd_records_nothing.rs` against the
   real CPU backend: the derivation for every marker, the scope's nesting,
   panic, and thread behaviour, and a `NoGrad` chain proven to leave the tape at
   zero while the identical `Grad` chain records and still backpropagates to the
   same numbers it did before.
8. [x] Run the row's evidence command plus `cargo fmt --check`,
   `cargo clippy --workspace -- -D warnings`, and `cargo test --workspace`;
   record concrete output. D-05 in this file's own numbering is `cpu/tape.rs`'s
   local decision, not Appendix C's D-005, so what lands in Appendix C is the
   three rulings this row actually makes: the tighten/install split, reading the
   result's marker rather than the receiver's, and where the gate lives.

## Boundaries

The tape stays where it is. GRD-003 makes tape nodes backend-neutral and
GRD-006 deletes the three backend-local ones; this row changes *whether* an
entry is pushed, not who owns it.

"Saves nothing" is discharged at the push boundary, not at the capture. A CPU
backward closure clones its saved operands into the `TapeEntry` immediately
before pushing it, so a refused push drops those clones at once and retains
nothing — but it does not prevent the clone. `CpuStorage` is `Rc`-backed, so
what is skipped is a refcount bump rather than a buffer copy. Never building
the entry needs the entry to be built lazily, which is a change to all 116 call
sites and to a `TapeEntry` type GRD-003 is about to replace. It belongs there.
