A row here is a canonical capability decision, not a claim about a machine. It
says what this build of Incin would run if the device were present; `cargo incin
doctor` reports whether it is. The registry is queried from the same canonical
declaration used to generate this document, and every advertised operation is
also required to satisfy the compile-time `Execute<O>` contract. `EXE-005`
runtime suites exercise representative and boundary behavior; they do not
execute every dtype, layout, rank, or training boundary represented below.

`PROPOSALS.md` §2.10 requires that support tables be generated from the
capability registrations rather than maintained beside them. These are those
registrations.

A backend advertises an operation for a set of element types, memory layouts and
ranks. Anything it does not advertise is unsupported, and is reported as such by
the capability registry rather than by a trait method that returns an error at
run time.

## Reading this

- **Element types** are the dtypes the rule covers. A dtype absent from every rule for an operation is refused by the registry, which is what lets a planner ask before it allocates.
- **Layouts** are `LayoutClass` values. `contiguous` is dense row-major; `strided` means the kernel handles a non-dense view without a copy.
- **Rank** is the tensor rank the rule accepts. `any` is an unbounded rank rule, the single workspace ceiling.
- **Training** says whether the rule also covers the backward pass. A rule with `no` still runs under inference.
- **Implementation** is `native` for a dedicated kernel and `composed` for an operation built from others. Both execute; they differ in cost.
