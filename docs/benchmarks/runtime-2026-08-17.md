## The cause: allocations per operation, not the capability scan

The first version of this document guessed that the canonical dispatch path's
per-operand capability admission was responsible. **That guess was wrong**, and
it is recorded here rather than quietly replaced because it was wrong in an
instructive way: it named the newest thing on the path instead of measuring.

Measured directly, with a counting global allocator and a timing loop over the
same tree:

| Measurement | Value |
|---|---:|
| `CapabilityRegistry::support(add/f32/rank1)` | 22 ns |
| `CapabilityRegistry::support(zeros/f32/rank1)` | 44 ns |
| `CapabilityQuery` clone | 2.5 ns |
| `add_exact` on **1** element (pure overhead) | 969 ns |
| `add_exact` on 1024 elements | 1788 ns |
| **heap allocations per `add_exact`, any size** | **23** |

Two capability queries account for ~45 ns of a 969 ns fixed overhead. The
linear scan over 176 `CapabilityRule` rows is not the problem. The 23
allocations are: at roughly 40 ns for an allocate/free pair, they are very
nearly the whole of it. The overhead is flat in tensor size, which is what a
per-call allocation count looks like rather than what a compute regression looks
like.

**There are two separate problems, and this is only the first.** A fixed ~1 µs
cannot explain the 65536-element series, which is 58 µs against a 6.7 µs
baseline: a 51 µs gap. That series is compute-dominated, and 58 µs for 65536
`f32` adds is about 0.9 ns per element, roughly an order of magnitude off what a
plain scalar loop over contiguous memory achieves. The elementwise kernel's
per-element cost is a second, independent regression, and nothing below
addresses it. See "What is still open".

Attributed by capturing a backtrace at every allocation during exactly one
`add_exact`, the 23 fell into four groups:

1. **Output shape inference ran twice.** `infer_outputs` derives the output
   metadata, then `verify_outputs` re-derives it through the same
   `expected_output` function to check the first result. For derived outputs
   that comparison can only ever agree.
2. **`broadcast_shape` round-tripped its accumulator** through a `ShapeBuf` and
   back into a `Vec` on every operand, then copied the result out again.
3. **`inferred_shape` materialised the first input's dims eagerly**, before the
   `match` that decides whether any branch reads them, which broadcast,
   matmul, and reduction rules do not.
4. **Autograd tape entries were built under `NoGrad`.** `Tape::push` discards
   an entry when the effective `GradMode` does not record, but the entry's
   saved shapes, input-id vector, and boxed backward closure were all allocated
   before the call could refuse them.

## What was changed

Each change is a pure optimisation: no check was removed, and the derived-output
path still validates output shape well-formedness.

- `OutputProvenance` distinguishes outputs derived by `infer_outputs` in the
  same call from outputs stated from outside. `verify_outputs` skips only the
  re-derivation for the former, and keeps every other check for both. This also
  established that **no production path supplies outputs** (both lowering
  entry points derive them), so the fabrication check exists for the descriptor
  test suite, and `validate` is now `#[cfg(test)]` to say so.
- `broadcast_shape` folds in place, seeded with the first shape rather than a
  scalar; `broadcast_input_shapes` folds over the inputs without first
  collecting a `Vec<&[usize]>`.
- `inferred_shape` computes the first input's dims lazily.
- `Tensor::from_shape_value` compares shape slices instead of allocating both
  sides to compare them.
- `infer_typed` compares against the typed shape's borrowed buffer instead of
  `ShapeValue::dims`, which allocates.
- `cpu::tape::push_with` takes a closure and consults `GradMode` before calling
  it. 49 call sites across the CPU operation modules were converted, and the
  saved-shape allocations in the elementwise binary operations moved inside.
- `ValidatedInvocation` no longer keeps its own `Vec<LogicalTensorMeta>`. The
  descriptor it wraps already owned an identical copy, built by cloning the
  first; `inputs()` borrows from the descriptor instead.
- `broadcast_input_shapes` takes operands that already agree as their own
  broadcast, which is the ordinary elementwise case.
- Shape inference produces a `ShapeBuf` throughout rather than a `Vec<usize>`
  that `infer_outputs` then copied into one. `ShapeBuf` stores rank 8 and below
  inline, so an ordinary rank now reaches the descriptor without touching the
  heap at all. `inferred_shape`, `transformed_shape`, `broadcast_shape` and
  every output rule were converted together.

Result on the same machine, by direct measurement. **These are intermediate
figures**, taken after the descriptor work and before the kernel and tape work
below; the current counts are in "Where the series stand now".

## What is still open

**Five allocations per aligned elementwise operation remain, from a starting
27**, and two of those five hold the result: the output data buffer and the
`Arc` around it. Three allocations of metadata survive on the whole path.

`CpuStorage` did *not* hold its geometry on the heap. An earlier version of
this list claimed it did. `TensorMeta` already stores `ShapeBuf`/`StrideBuf`
inline. What allocated was the plumbing either side of it:
`checked_contiguous_strides` computed an inline `StrideBuf` and then copied it
into a `Vec`, and `try_from_parts` took owned `Vec`s that it immediately
converted back. Both now pass the inline forms through.

What is left:

- The `Vec<LogicalTensorMeta>` the dispatch entry point builds for the inputs.
- The 55 `tape::push` call sites in the CUDA and Metal backends have not been
  converted to `push_with`. WGPU's 28 have; CUDA and Metal cannot be executed
  here, and a lazy-construction change there would be compile-checked only.
- One further allocation inside the CPU kernel's own bookkeeping.

Once `CpuStorage`'s constructors took slices, `clippy::unnecessary_to_owned`
found 61 more redundant `to_vec()` calls across the CPU backend that had been
invisible while the parameter was an owned `Vec`. Applying them took a rank-2
unary from 5 allocations to 4. The lint is a better detector for this class than
reading the code was.

Two earlier entries on this list were wrong.

The first claimed the outputs metadata vector was gone once shapes inlined. It
is not. `infer_outputs` still does `Vec::with_capacity(count)`, and the
allocation attribution below catches it at 176 bytes on every single-output
call. Inlining the shape removed the *second* allocation behind the vector, not
the vector itself. The entry is corrected above rather than deleted, because the
claim was measured and repeated and is worth knowing was wrong.

The second: the CPU executor does
**not** recompute the broadcast in a release build. `resolved_output_shape`
takes the descriptor's answer, and `layout::broadcast_shape` runs only inside a
`debug_assert_eq!` that checks the two agree. The allocation attribution above
had been read from a debug build.

### The second cause: the SIMD kernels were unreachable

Found and fixed. The AVX2 elementwise kernels were gated on a *compile-time*
constant:

```rust
const LANES: usize = crate::simd::simd_lanes::<f32>();
if LANES >= 8 { /* AVX2 path */ }
```

`simd_lanes` reads `cfg!(target_feature = "avx2")`. A stock
`cargo build --release` for `x86_64-unknown-linux-gnu` targets the baseline ISA,
where that is false, `LANES` is 4, and the whole branch is dead code. **Every
default build fell through to the scalar loop**, which is what users installing
from crates.io would have got, and what the benchmark was measuring. The
kernels themselves were correct and complete; nothing could reach them.

The recorded baselines were captured on a build that reached the AVX2 kernels,
which is why they looked unreachable from here. They needed no special flags to
do it: at the revision that captured them the gate was
`std::arch::is_x86_feature_detected!("avx2")`, a runtime check, and the
compile-time constant replaced it 44 commits later. See "Where the baselines
actually came from". Reproducing that reach on the current tree with
`RUSTFLAGS="-C target-feature=+avx2,+fma"`:

| Series | stock build | `+avx2` build | recorded baseline |
|---|---:|---:|---:|
| `eager/add_f32/1024` | 1.66 µs | 835 ns | 426.7 ns |
| `eager/add_f32/65536` | 60.7 µs | **6.58 µs** | **6.68 µs** |

The large series matches its baseline to within 2%. That is the whole of the
"8.7x regression".

The fix is the standard pattern the kernels were already written for: they carry
`#[target_feature(enable = "avx2")]`, which is precisely what makes them
compile on a baseline target and callable once the feature is proven present at
run time. `simd::avx2_detected()` is that proof, cached in a relaxed atomic so
the hot-path check is a single load, and each gate became
`LANES >= 8 || avx2_detected()`. Compile-time AVX2 builds are unaffected; a
machine without AVX2 still takes the scalar path.

Note what this means for testing: two existing tests in
`elementwise_kernel.rs` already used runtime detection, so they exercised the
AVX2 kernels. The *production* path did not. A kernel can be tested and still
be unreachable, the same shape of defect as the WGPU activations that had
shaders and executors but no capability rows.

The divergence was the mechanism. The test helper predicting which kernel would
run was written `simd_lanes::<f32>() >= 8 || is_x86_feature_detected!("avx2")`,
while the production gate four functions away read the constant alone. Two
spellings of one decision, and only one of them was right. `matmul.rs` and
`quant.rs` had it right all along, which is why `matmul_f32/64` never showed the
gap. Every AVX2 decision in the crate now goes through `simd::avx2_detected` or
`simd::avx2_fma_detected`, the elementwise gate is one named function per element
type, and a test asserts that function opens on a machine that supports the
instructions, verified to fail with a precise message when the gate is
narrowed back.

## The third cause: whole-tensor reductions had no dense path

`sum_all` and its siblings walked a logical odometer and read every element
through `CpuStorage::get`, a stride dot product over a heap-allocated index
vector, then a match on the buffer behind an `Arc`, per element. About twenty
cycles to fetch one number and one to add it. A 1024-element `sum_all` measured
6.8 ns per element for that reason; the *baseline* for the series was 4.5 ns per
element, so this was slow before the descriptor work and not a regression at all.

`DenseReader` reads a contiguous typed buffer directly, and `fold_all_f64` runs
the same fold closure over either the dense reader or the odometer, sharing the
closure is what makes the two paths agree by construction. `sum_all`,
`mean_all`, `prod_all`, `max_all`, and `min_all` are converted. The accumulator
stays `f64` and the traversal order is unchanged, so results are bit-identical:
summing `f32` in `f32` would be faster again and would silently change every
reduced value. `max_all`/`min_all` keep strict comparisons, so the winning index
their gradients record is still the first of equal extrema.

Isolated, `sum_f32/1024` went from 6.97 µs to 1.32 µs and `sum_f32/65536` from
399 µs to 44 µs. Under the full suite, where the operands are no longer cache-hot,
the same series measure 5.41 µs and 306 µs, both inside budget. The isolated
figure is the kernel; the suite figure is what the gate reads.

## Where the baselines actually came from

`docs/plan/baselines/main.toml` records `revision = a4ddb32`, and an A/B against
that revision is not possible, for a reason the file states itself: it also
records `worktree = "dirty: SHP-007, SHP-008, and GOV-004 implementation under
verification"`. The benchmark harness `crates/incin/benches/baselines.rs` does
not exist at `a4ddb32`. It arrives in `16156c8`, the immediate child, together
with the baselines file. The recorded revision is the parent of the tree that
was measured, not the tree that was measured, and that tree was never committed
in that state.

`16156c8` is therefore the closest revision that can be built and benchmarked,
and it is the right comparison point. Two things about it are not
apples-to-apples with the present tree. Both were later tested rather than
assumed, in "The A/B was run" below, and neither turned out to carry the gap:

- **Toolchain.** The baselines were taken on `rustc 1.92.0`; `rust-toolchain.toml`
  now pins `1.97.1`. The pin exists because trybuild fixtures record rustc
  diagnostic text, so it is not a free variable.
- **Criterion.** The baselines were taken on `criterion 0.5.1`; the workspace is
  now on `0.8.2`. Sampling and outlier handling are not guaranteed identical
  across a major version.

What *can* be established from the history without running anything, and what
settles the elementwise question:

`248f0af`, a commit titled "ledger updates + b4 clippy fix", replaced
`std::arch::is_x86_feature_detected!("avx2")` with the compile-time
`LANES >= 8` constant in `elementwise_kernel.rs`. It is 44 commits after the
baseline capture. It touched `docs/plan/baselines/main.toml` in the same commit
and appended only a `[[memory]]` and a `[[cache]]` row; it did not rebase a
single runtime series. So the recorded `add_f32` numbers are pre-regression
figures, the regression rode in unmeasured behind a housekeeping title, and the
`add_f32/65536` series has been comparing a scalar build against an AVX2
baseline ever since. Restoring runtime detection restored the comparison: that
series now measures 5.85 µs against a 5.34 µs baseline and a 6.68 µs ceiling.

This is also why a `git bisect` on the benchmark would not have found it. The
series was inside its budget at capture, went outside it in a commit that
changed no benchmark and no baseline, and nothing ran the budget gate against
fresh measurements in between.

stock `cargo bench`, no `RUSTFLAGS`, no `target-cpu=native`, `--features cpu`
in both cases.

## What actually changed: the baselines predate the execution architecture

At `16156c8`, `crates/incin-core/src/exec/` contains four files: `mod.rs`,
`proof.rs`, `rule.rs`, `spec.rs`. There is no `catalog.rs` and no `dispatch.rs`.
The canonical execution path did not exist when the baselines were captured.
`Tensor::zeros` at that revision is one line:

```rust
let inner = B::zeros(dims.as_ref(), dtype, &device)?;
```

The dates line up exactly:

- `docs/plan/baselines/main.toml` last touched **2026-07-31** by `248f0af`.
- `catalog.rs` added **2026-08-03** by `93beef1`, "refactor(fnd-004):
  canonicalize operation semantics and descriptors".
- `dispatch.rs` added **2026-08-03** by `43fd02f`, "feat(fnd-005): establish
  the canonical CPU execution path".

`git rev-list --count 16156c8..HEAD` is **1121**.

So the three failing small-input series are not measuring a regression against
a comparable predecessor. They are measuring the cost of an execution
architecture against ceilings captured three days and 1121 commits before that
architecture landed, by a benchmark that was never rebased when it landed.

The backend work itself did not regress. `cpu::creation::zeros` at `16156c8` is
`fill_buffer` followed by `CpuStorage::from_contiguous`; `zeros_with_total` in
the current tree is the same two calls, and does slightly less work because the
element count arrives already computed. The kernel is not the difference.

## Where the fixed cost actually goes

Two harnesses were used, both temporary and neither committed: a
backtrace-capturing global allocator for the allocation table, and a staged
timing harness that calls the same public entry points the dispatcher calls.
Both in release. The timing figures below are the median of three runs whose
spread was under 5 ns on every stage.

### Rank-1 `zeros`, the `f32_create` series

Five allocations, of which two are the result and three are metadata.

| # | bytes | site | owner | kind | survives call |
|---|---:|---|---|---|---|
| 0 | 8 | `Tensor::zeros`, `<[usize]>::to_vec` | `CreationAttributes.shape: Vec<usize>` | metadata | no |
| 1 | 176 | `infer_outputs`, `Vec::with_capacity(1)` | `Descriptor` output metadata | metadata | no |
| 2 | 4 | `cpu::creation::fill_buffer` | `Vec<f32>` | **result data** | yes |
| 3 | 48 | `CpuStorage::try_from_contiguous` | `Arc<CpuBuffer>` | **result** | yes |
| 4 | 8 | `Tensor::try_from_storage`, `<[usize]>::to_vec` | typed frontend dims | metadata | yes |

Allocations 2 and 3 are the tensor. Allocation 4 is the frontend's own record of
its dimensions and outlives the call. Allocations 0 and 1 are transient
descriptor metadata, live only for the duration of the dispatch, and are the
only two that a representation change could remove.

Latency, 497.6 ns total:

| Stage | ns | share | existed at `16156c8` |
|---|---:|---:|---|
| `CreationAttributes` construction | 12.0 | 2% | no |
| descriptor construction and validation | 88.0 | 18% | no |
| capability query build and registry scan | 62.5 | 13% | no |
| backend execute, payload validation, output verification | 183.1 | 37% | partly |
| typed frontend prep and `from_parts` | 156.0 | 31% | partly |

The last two rows cannot be split further from outside the crate because
`ValidatedInvocation::validated()` is private, so no test can build an
`ExecutionRequest` and call `Execute` in isolation. What bounds them is the
historical measurement: the whole call at `16156c8`, backend included, was
86.4 ns. Every stage in this table except the raw kernel is therefore new or
grown, and the raw kernel is a fraction of 86 ns.

### Rank-2 aligned `try_add`

Four allocations in release, five in debug.

| # | bytes | site | kind |
|---|---:|---|---|
| 0 | 352 | `execute_shaped_with_payload`, `Vec<LogicalTensorMeta>` for 2 inputs | metadata |
| 1 | 176 | `infer_outputs`, `Vec<LogicalTensorMeta>` for 1 output | metadata |
| 2 | 2048 | `elementwise_kernel::avx2_binary_f32` | **result data** |
| 3 | 48 | `CpuStorage`, `Arc<CpuBuffer>` | **result** |

The debug-only fifth allocation is 16 bytes from `broadcast_dim_slices`, reached
through `layout::broadcast_shape` inside a `debug_assert_eq!`. It is not present
in release. This confirms the correction already recorded above: the committed
ceiling of 5 in `crates/incin/tests/hot_path_allocations.rs` is a `cargo test`
figure, and release is one lower.

Latency at 1024 elements, 687.7 ns total: 36.2 ns to build the input metadata
vector, 103.9 ns for descriptor construction and validation on top of it, and
547.8 ns for everything else, which includes the capability query, the backend
AVX2 kernel over 1024 f32, output verification and the typed frontend.

### Rank-2 unary `relu`

Four allocations: 176 for the input `Vec<LogicalTensorMeta>`, 176 for the output
one, 2048 for the result data in `map_unary_typed`, 48 for the `Arc`. Same
shape of story as `add`, with one input instead of two.

### The metadata cost, stated exactly

On the elementwise path in a release build the entire remaining metadata cost is
**two `Vec<LogicalTensorMeta>` allocations, one for inputs and one for outputs**,
at 176 bytes per element. `LogicalTensorMeta` is 176 bytes because it holds
`Option<ShapeBuf>`, and `ShapeBuf` inlines up to `INLINE_RANK` = 8 dimensions.

It cannot use `InlineOrHeap` itself: `InlineOrHeap<T>` requires `T: Copy +
Default`, and `LogicalTensorMeta` is not `Copy` because of the owned `ShapeBuf`
inside it.

Removing both allocations is worth roughly 120 ns of allocate and free on this
machine. That does not close a 411 ns gap. The rest is the canonical path doing
its job: catalog lookup, attribute validation, output inference, output
verification, rank and device agreement checks, the capability registry scan,
`ExecutionContext` construction and `ShapeValue::try_new`.

## Decision: the architecture is correct and the small-input budgets are stale

The evidence supports one reading. The three failing series measure work that
the canonical execution path is supposed to do, against ceilings recorded before
that path existed, on a machine that still reproduces those ceilings for the
code they were taken from. That is a budget that was never rebased, not a
regression.

Options considered, and why they are not taken now:

- **Purpose-built inline vector without the `Copy` bound.** The obvious
  mechanical fix: a small-vector type that can hold `LogicalTensorMeta` inline
  and remove both allocations. It buys about 120 ns of the roughly 411 ns gap
  and adds a hand-written container with its own drop and growth logic to a
  crate whose existing inline storage is deliberately restricted to `Copy`
  element types precisely so it needs no such logic. Worth revisiting, but not
  as the answer to a stale budget.
- **Borrowed metadata in the descriptor.** Would remove the allocations without
  a new container, at the cost of a lifetime parameter on `Descriptor`,
  `ValidatedInvocation` and everything they touch, including the public backend
  authoring surface. That is a large public API change bought with 120 ns.
- **Fixed-arity representation.** Most operations have one or two inputs, so an
  enum over small arities would cover nearly everything. It makes variadic and
  custom operations a second-class case, which the brief rules out.
- **Splitting the owned descriptor from a borrowed eager view.** This is the
  honest version of the borrowed-metadata option and the one to reach for if the
  cost ever has to come out. It also duplicates the validation surface, which is
  the exact thing the canonical path was built to stop.
- **Caching immutable logical metadata.** Shape, dtype and device are already
  owned by the tensor; the metadata vector is a per-call copy of facts that
  already exist. A cache invalidation story for that is a larger correctness
  risk than the 120 ns is worth.
- **Bypassing the descriptor on a fast path.** Ruled out by the brief and
  correctly so. A second execution path is a second place for validation,
  dtype and gradient semantics to diverge.

None of these should be undertaken to make a stale number green.

**Recommendation, for the maintainer to make and not for this pass to apply:**
re-capture `docs/plan/baselines/main.toml` and the small-input entries in
`docs/plan/budgets.toml` against the current canonical architecture, on a
recorded machine, and record in the baselines file that the previous figures
were taken before `93beef1` and `43fd02f`. The three large-input series and the
matmul series should keep their current ceilings, which the current tree meets.

`docs/plan/budgets.toml` has not been changed by this pass. Changing it is the
recommendation, not the action.

## The CUDA and Metal tape sites: verified, not converted

The open item above was to convert the remaining `tape::push` call sites in the
CUDA and Metal backends to `push_with`, the way the CPU and WGPU backends were.
That work is deliberately not done, and the reason is worth recording because
it is not "no hardware".

There are 20 sites in `cuda/backend.rs` and 35 in `metal/backend.rs`.

**The semantics do match.** `push_with(|| entry)` is `if
GradMode::current().records() { push(entry()) }`, and `Tape::push` in
`incin-core/src/exec/tape.rs:214` already carries the same
`GradMode::current().records()` gate. The backend `push` is the thread-local
lookup plus telemetry on top of that. The double gate cannot double-record and
cannot skip a recording that `push` would have made, because both read the same
value and the closure is only skipped when `push` would itself have discarded
the entry. Ownership is likewise unchanged: `push_with` takes `FnOnce`, so the
entry is moved exactly once, as it is when passed by value.

**But a mechanical rewrite would buy nothing.** Neither backend has a
`push_with` at all; it would have to be added, mirroring cpu and wgpu. More to
the point, the CUDA and Metal call sites prepare their captures *outside* the
`TapeEntry { .. }` expression:

```rust
let mask_cap = mask_b.clone();
let (true_id, false_id, out_id) = (true_b.id, false_b.id, out_storage.id);
crate::cuda::tape::push(crate::cuda::tape::TapeEntry { .. });
```

Rewriting `push(x)` to `push_with(|| x)` would elide the struct literal and
nothing else. The clones and `to_vec`s that are the actual cost have already
run by then. Getting the benefit means moving those preparatory lines inside
the closure, site by site. That is safe in principle for CUDA, where
`CudaStorage` is a derived `Clone` over `Arc<CudaBuffer>` plus inline metadata
so the clone is pure, but it is 55 individual judgements about what is safe to
defer, and none of them can be executed on this machine. It is queued for
hardware, not attempted blind.

One thing found while reading, unrelated to performance: `metal::tape::push` is
`pub`, while the cpu and cuda equivalents are `pub(crate)`. `wgpu::tape` has
both, `push_with` crate-private and `push` public. That asymmetry looks
accidental rather than intended and is worth a look independently of this work.
